II. Software Requirement Specification
1. Product Overview
NexaLab is a web-based learning platform for Vietnamese lower-secondary (THCS) Natural Science, aligned with the 2018 general education curriculum. It combines a familiar learning path with deterministic virtual labs and practical challenges, so students can learn, act, observe, retry and review evidence of their progress. It runs in the browser on desktop and mobile; no lab equipment or chemicals are needed.
Release 1 closes two gaps. The practice gap: students need to do more than consume content. The diagnostic gap: the platform must keep trustworthy evidence that teachers can use later. Delivery is student-first: the first increment is usable by students, while identity, ownership and authorization support all four roles from the start.
The platform serves four user roles. Students follow assigned lessons, take quizzes, run lab experiments and review their own progress. Teachers manage their own classes, assign content and review student evidence. Parents follow a linked child's progress in read-only mode. Admins manage users, content, subjects, labs and assets.
The student loop is Learn → Quiz → Practice/Simulation → Challenge → Retry → Progress. Inside a lesson, the ordered path is Reading → Video → Study cards → Quiz → Lab/Practice → Challenge. Later steps stay visible but locked until the earlier gate is met, and the server, not the client, decides access and official completion.
Two principles shape the system. First, only the deterministic Simulation Engine and Challenge Evaluator determine official results and verdicts; the backend recomputes every simulation, and client previews are never official. Second, every score, count or status shown to a user can be traced back to the content or attempts behind it.
The Release 1 pilot runs in one school with up to two Grade 8 classes and at most 80 students; Grade 9 is a later direction. The Grade 8 electric-circuit lab is the representative lab and challenge for Increment A. The current product also has a human-eye model and fixed Chemistry reactions, which stay in Release 1 but are not yet assigned to an increment:

3.4.3 Function: Run Simulation
Trigger: Run. Description: shows an instant client preview, then the official server result (UC-LAB-04, UC-LAB-08).
Function details

=== PAGE 105 ===
1. The client runs the same versioned packages/sim for an instant preview. The preview never decides the stored result or verdict.
2. The client sends POST /attempts with lessonStepId, challengeId, labState, durationMs and an idempotency key. The student and the assignment are derived on the server; any result or verdict sent by the client is ignored.
3. The server checks the step, challenge and lab belong together and that the gate is open, rejects invalid or oversized states before simulating, and applies a rate limit (MSG-46).

3.4.4 Function: Challenge Grading
Trigger: Run inside SC-15. Description: grades the official result against successConditions (UC-LAB-05).
Function details
1. SC-15 shows the objective, the allowed components and the constraints, for example maxCurrentMa = 20.
2. NS-09 decides the verdict: all conditions met → passed (MSG-25); some met → partial (MSG-26); minimum not met → needs_practice (MSG-27).
3. The result lists each condition as met or not met. 4. The challenge step completes only on passed; partial and needs_practice leave it in progress (BR-28). Completing it unlocks the next configured step.
5. Any verdict other than passed offers Retry; each retry is a new Attempt, and earlier attempts are never changed.
6. A successConditions field missing from simulationResult stops grading and reports MSG-24 to admins; the student sees MSG-43 and is not blamed.

Not in Release 1 Increment A: Student AI Tutor, Teacher AI Content Assistant, leaderboards, gamification economies and advanced analytics. 5.4.2 Verification Evidence Levels
Every ticket and release claim states which level it has reached (PRD §8). Integration and E2E tests count as passed only when their real database, API, seed and browser dependencies actually ran.
1. Source verification: the implementation and authorization paths are traced in code. 2. Automated verification: the relevant unit, typecheck, lint and build commands pass. 3. Runtime verification: the real configured API, database, seed data and browser path are exercised.
4. Production verification: the deployed environment is exercised; never inferred from local success.
5.4.3 Definition of Done
A use case is done when all of the following hold:
1. Its main, alternative and exception flows are implemented. 2. All acceptance criteria of its feature pass. 3. Authorization is tested at the API, not only in the UI (BR-01). 4. For lab use cases, unit tests against textbook figures pass, the scientific model is documented and BR-12 review is done.
5. The related quality targets in 4.2 are met, with responsive and accessibility evidence for student screens.
6. A Playwright scenario exists if the use case lies on the Increment A student journey. 7. For Future AI use cases, every AI response has a traceable HintLog (BR-13).
5.4.4 Release 1 Outcome Gates
Increment A is ready for pilot review when a provisioned student completes the assigned path from login to progress with real seeded dependencies, cross-user and cross-class access is refused, the representative simulation result and verdict are server-authoritative, and responsive and accessibility checks have evidence.
