# Object storage (Cloudflare R2)

Owner-facing runbook for NexaLab's private object storage: what lives where, how objects are created and removed,
the bucket settings the app depends on, and the checklist for creating the pilot and production buckets.
Story acc-6 of `increment-account-notifications-r2`. Decisions: D19 (binaries in private R2, metadata in PostgreSQL),
D-ACC-03 (private avatars), D-ACC-04 (dev bucket for avatars; pilot/production creation documented, not performed).

Status on 2026-10-21: only the development bucket `nexalab-dev` exists. Pilot and production buckets have **not** been
created; follow §6 when the owner approves them.

## 1. Principles

- **Private bucket only.** No public access, no `r2.dev` subdomain and no custom domain. Browsers only ever receive
  short-lived presigned URLs created by the API.
- **Credentials stay on the server.** `R2_*` variables are backend-only (never `VITE_*`). The client never chooses a
  bucket, key or scope; every key is generated by the server.
- **One bucket per environment**, and every key also starts with `APP_ENV` (`development`, `test`, `pilot`,
  `production`), so an object written by one environment can never be mistaken for another's.
- **Staging is separate from released objects.** Uploads land under `<env>/staging/…`, are checked by the server, then
  copied to their released key. Anything left in staging is disposable, which is what the lifecycle rule in §4 relies on.

## 2. Configuration

| Variable | Meaning |
| --- | --- |
| `ASSET_STORAGE` | `r2` uses Cloudflare R2. Anything else uses the local driver (`UPLOAD_DIR/objects`, HMAC-signed API URLs), for development and tests only. |
| `APP_ENV` | Key prefix: `development`, `test`, `pilot` or `production` (anything else falls back to `development`). |
| `R2_BUCKET` | Bucket name, for example `nexalab-dev`. |
| `R2_ENDPOINT` | `https://<account-id>.r2.cloudflarestorage.com` (use the jurisdiction endpoint if the bucket has one). |
| `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | S3 credentials of a bucket-scoped API token (§5). |
| `R2_UPLOAD_TTL_SECONDS` | Presigned PUT/part lifetime, clamped to 60–3600 s (default 900). |
| `R2_READ_TTL_SECONDS` | Presigned GET lifetime, clamped to 30–3600 s (default 300). The FE refetches the profile every 4 minutes so avatar URLs never expire on screen. |
| `WEB_ORIGIN` | Comma-separated web origins allowed by the API's own CORS; the bucket CORS rule (§4) must list the same origins. |

`storage()` refuses to start with `ASSET_STORAGE=r2` when any of `R2_BUCKET`, `R2_ENDPOINT`, `R2_ACCESS_KEY_ID` or
`R2_SECRET_ACCESS_KEY` is missing or still contains a `<placeholder>`.

## 3. Key layout and lifecycle

| Prefix | Written by | Removed by |
| --- | --- | --- |
| `<env>/staging/<assetId>/<versionId>/<file>` | Browser, presigned PUT or multipart upload (CF-T2 assets) | Finalize copies it to the released key and deletes it; a failed check deletes it; `cleanupExpiredUploads` aborts and deletes PENDING uploads older than the 24 h upload window; the lifecycle rule catches anything else |
| `<env>/assets/shared/<assetId>/<versionId>/<file>` | Server copy on finalize, shared-library assets | Admin delete (`DELETE /admin/assets/:id`), refused while a lesson or lab references it |
| `<env>/assets/private/<assetId>/<versionId>/<file>` | Server copy on finalize, a teacher's private assets | As above |
| `<env>/staging/avatars/<userId>/<uuid>.<png\|jpg\|webp>` | Browser, presigned PUT from `POST /me/avatar/upload-url` | `POST /me/avatar` copies it to the avatar key and deletes it; an upload that is never confirmed is expired by the lifecycle rule |
| `<env>/avatars/<userId>/<uuid>.<png\|jpg\|webp>` | Server copy on confirmation | Replaced or removed avatar (own, owning teacher, admin), and permanent account deletion |
| `<env>/staging/r2-check-<id>/…` | `npm run r2:check` probes | The check deletes every probe at the end |

### Avatar lifecycle (D-ACC-03)

1. `POST /me/avatar/upload-url` with `{ contentType, bytes }`: PNG, JPEG or WebP, at most 2 MB. Every role may upload.
   The API returns a presigned PUT for a fresh key under the caller's own staging prefix.
2. The browser PUTs the file straight to R2 (bucket CORS, §4).
3. `POST /me/avatar` with `{ key }`: the key must sit under the caller's own staging prefix, be a single segment with a
   known extension, and the stored object must exist, be at most 2 MB and carry an allowed type (checked with a server
   HEAD, not the client's claim). The server copies it to `<env>/avatars/<userId>/…`, deletes the staging object,
   stores the key on `User.avatarKey`, deletes the previous avatar object and writes an audit entry.
4. Reading: `GET /me/profile` returns `avatarUrl`, a presigned GET valid for `R2_READ_TTL_SECONDS`. Avatars are never
   public. Only signed-in users receive these URLs.
5. Removal: `DELETE /me/avatar` (own), `DELETE /classes/:classId/students/:studentId/avatar` (owning teacher of an
   approved member) and `DELETE /admin/users/:id/avatar` (admin). Each one clears the key, deletes the object and is audited.
6. Permanent account deletion (`DELETE /admin/users/:id`) deletes the avatar object after the account row is gone.
   Disabling an account keeps it, so a reactivated account still has its picture.

Avatars confirmed before 2026-10-21 were uploaded straight to `<env>/avatars/…`; they keep working because the stored
key is used as-is.

## 4. Bucket settings the app depends on

The app's API token can only read and write objects: reading bucket settings with it returns `AccessDenied`
(verified on `nexalab-dev` on 2026-10-21). Bucket settings are therefore set by the owner in the Cloudflare dashboard
(R2 → bucket → Settings) or with `wrangler`.

### CORS

Browsers upload directly to R2 and read avatar and media URLs from the web origin, so the bucket needs a CORS rule.
Multipart uploads read each part's `ETag`, so it must be exposed.

```json
[
  {
    "AllowedOrigins": ["https://<web-origin>"],
    "AllowedMethods": ["GET", "HEAD", "PUT"],
    "AllowedHeaders": ["content-type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

- Development: `http://localhost:5173` and `http://127.0.0.1:5173` (the Playwright suites use both).
- Pilot/production: only the exact deployed web origin(s), the same values as the API's `WEB_ORIGIN`. Never `*`.
- `POST` and `DELETE` are not needed: multipart create, complete and abort, as well as deletes, run server-side.

Evidence that the dev bucket's rule works: `acc-profile-live.spec.ts` (avatar PUT from the browser, image served from
a presigned GET) passes against `nexalab-dev`, and so did `cf-storage-live.spec.ts` (browser PUT and a 70 MB multipart
upload with ETags exposed), which lives on the FE branch `feat/content-foundation` and is not merged yet.

### Lifecycle rules

| Rule | Prefix | Action |
| --- | --- | --- |
| Expire abandoned uploads | `<env>/staging/` | Delete objects 2 days after upload (longer than the 24 h asset upload window, so nothing still being finalised is removed) |
| Abort stale multipart uploads | whole bucket | Abort incomplete multipart uploads after 1 day |

Use the environment's own prefix (`pilot/staging/` in the pilot bucket and so on). Do not add expiry rules to
`<env>/assets/` or `<env>/avatars/`: those objects are referenced from the database and removed only through the API.

## 5. API tokens

- One token per bucket: R2 → Manage API tokens → **Object Read & Write**, limited to that single bucket. Never use an
  account-wide or Admin token in the app.
- Put the token's Access Key ID and Secret Access Key in the backend secret store as `R2_ACCESS_KEY_ID` /
  `R2_SECRET_ACCESS_KEY`. They are shown once; never commit them or put them in a `VITE_*` variable.
- Rotation: create a new token, deploy it, run `npm run r2:check`, then revoke the old token.
- Bucket settings (§4) need a separate owner account or token that the app never holds.

## 6. Checklist: creating the pilot or production bucket

Not performed yet. Run it once per environment when the owner approves.

1. **Decide the inputs.** Account owner, environment (`pilot` or `production`), web origin(s), data location
   (location hint, or a jurisdiction if the school's data policy requires one), and the upload budgets once
   Q-DATA-01 / Q-C2-03 are answered.
2. **Create the bucket.** Name it `nexalab-pilot` or `nexalab-prod`. Standard storage class. Leave public access,
   the `r2.dev` subdomain and custom domains **off**.
3. **Set CORS** (§4) with the exact web origin(s).
4. **Add the lifecycle rules** (§4) with the environment's prefix.
5. **Create a bucket-scoped Object Read & Write token** (§5) and store it in the backend secret store.
6. **Configure the backend.** `ASSET_STORAGE=r2`, `APP_ENV=pilot|production`, `R2_BUCKET`, `R2_ENDPOINT`,
   `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `WEB_ORIGIN`, `R2_UPLOAD_TTL_SECONDS`, `R2_READ_TTL_SECONDS`. Set
   `ASSET_BUDGETS_APPROVED=true` only after the budgets are approved, and set `MALWARE_SCANNER_URL`: without a scanner,
   pilot/production uploads never become READY.
7. **Verify.**
   - `npm run r2:check`: expect `RESULT ok` (9 checks).
   - From the deployed web app: upload, view and remove an avatar, and upload one asset; then confirm in the bucket
     that `<env>/staging/` is empty and the released objects exist.
   - Confirm that an unsigned GET of any object returns 403 or 404.
8. **Record it.** Add the bucket, region or jurisdiction, origins, token name (never the secret), date and the
   `r2:check` result to `sprint-status.yaml` under the increment, and note who holds the owner credentials.

Never copy development objects into pilot or production: they contain test fixtures and synthetic content.

## 7. Verification commands

```bash
npm run r2:check          # end-to-end object checks against the configured storage (no secrets printed)
npm run test:cf           # CF-T2..T4 API checks (assets, ingestion, importer), cleans up after itself
# FE, with the API and Vite running against the same storage:
PLAYWRIGHT_CHANNEL=chrome npx playwright test tests/acc-profile-live.spec.ts
# tests/cf-storage-live.spec.ts (multipart through bucket CORS) is on feat/content-foundation until that branch merges.
```
