# Foundational Lab track: portfolio, archetypes and blueprints

## Curriculum and selection

Use source-backed Outcome proposals and independent mapping review. Do not infer official approval from an ACTIVE database lifecycle state. The KHTN8–9 catalog records 30 discovery candidates and an illustrative ~20-candidate shortlist, not final coverage. Preserve all original IDs and reasons. One model can serve several activities and grades; a release binds exact versions. Real practical skill may need teacher observation outside the virtual Lab.

For each candidate record source/Outcome proposal, observable action, model scope, valid observations, evidence, pedagogy, risks, family, activity, archetype, modality, reuse dimensions, disposition and review status. KEEP, MERGE, SHARE, SPLIT, DEFER and NO LAB are proposal decisions, not reviewer approvals.

## Reusable interaction strategy

| Archetype | Interaction | Possible reuse | Example |
|---|---|---|---|
| Builder / topology | assemble and connect | selection, connections, keyboard alternative | circuits |
| Parameter explorer | vary inputs and compare observations | sliders, table, graph | lever |
| Experiment bench | select tools/materials, measure | sample tray and measurement widgets | fluids, indicator |
| System dynamics | vary conditions over steps/time | time controls and data views | populations |
| Spatial interaction | rotate/place/explore relationships | camera and selection controls | anatomy, if needed |

Archetype and modality are independent. Choose 2D, 3D or both for the learning task and measured device limits. A Lab may use multiple archetypes. Start with the shared host and only the components justified by an implemented Lab; a family/workspace/renderer shared by two Labs does not mean identical model, activity, grading, Lab identity or release.

## Activity blueprint template

Record: candidate and Lab identity; proposed source and Outcome/lesson mapping and approval state; student objective and observable actions; ordered checkpoints; exact evidence schema; scientific observations; activity assessment rubric; model/version/schema, valid states, assumptions, limitations and safety; boundary/golden/invalid fixtures; modality/archetype/accessibility; asset provenance and budgets; release and Class Lab reuse constraints; reviewer roles and signed exact digest. Model observations and learning assessment are distinct.

The first instance is the bulb Circuit blueprint in ../spec-foundational-lab-p3-1/lab-definition.md. Its Outcome, model and rubric require actual reviewer approval before a reviewed pilot or release. Its LED predecessor remains a historical extension.

## Reuse and QA

Each model owns deterministic state/output schemas and independently versioned behavior and fixtures; reuse the existing model registry and version objects where verified. Lab modules own renderers and copy; the host owns launch, submission, local draft and result display. Initial UI is 2D and accessible by keyboard; 3D assets are optional later and cannot change model or verdict.

For each Lab check curriculum/source alignment, independent numerical or logical scientific cases, scoring/rubric behavior, invalid states, authorization, idempotency, draft/recovery, pinning/replay, accessibility, device performance and safety/rights. Proposed budgets must be measured on agreed target devices; they are not evidence of performance. Release and reviewer gates are separate from the technical Build gate.
