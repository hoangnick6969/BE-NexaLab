- (constraint) No simulation, 3D asset, schema, publication, Outcome Normalizer, or Content Tool implementation is in P3.1 scope.
- (evidence) Pilot database contains exactly 47 non-synthetic released KHTN 8 Structured Lessons with pack provenance; additional grade-8 rows are synthetic fixtures and are excluded.
- (evidence) Pilot contains 51 released KHTN 9 lesson packs and active outcomes, but their manifest shape lacks KHTN 8-style source-block/page provenance and review metadata labels the publisher textbook as ORIGINAL; use only as conditional reuse evidence, not a verified release binding.
- (evidence) Current runtime allowlists circuit@1.0.0, chemistry@1.0.0, and eye@1.0.0; server simulation, attempts, idempotency, config/pack pinning, golden-case validation, and student access gates already exist.
- (evidence) Pilot Lab rows circuit, chemistry, and eye are CLASS_PRIVATE, not release-cleared, and have no topicCode; no SimulationConfigVersion, PracticalActivityVersion, SimulationPackVersion, or FoundationalCourseVersion rows exist.
- (decision) Recommend LED current-limiting DC circuit as the first Foundational Lab MVP because it covers KHTN 8 Lessons 21-25, conditionally extends to KHTN 9 electricity, and reuses the existing deterministic engine, React Flow workspace, attempt flow, and server-authoritative evaluation.
- (decision) The MVP scientific model is the existing idealized series/independent-parallel LED model: one ideal DC source, ideal wires/switches, resistors in each branch, fixed 2.0 V forward drop per red LED, and I=max(0,(U-2N)/R) per branch.
- (constraint) KHTN 8 Outcome codes are candidate mappings only even when stored on current Lesson rows; they must be labelled PROPOSED_UNAPPROVED and cannot clear a release gate.
- (decision) Foundational Lab is a reviewed reusable simulation; Class Lab is a teacher configuration of an approved Lab using allowlisted parameters and does not alter scientific equations.
- (gap) The first implementation requires scientific/range approval, immutable activity/config/simulation-pack versions, released Lesson bindings, and FE manifest-driven discovery; it does not require a database migration.
- (event) Validation pass 1 PASS: four capabilities include intent and success, catalog has ten ranked candidates, MVP defines fourteen golden cases and five exact released Lesson bindings.
- (event) Validation pass 2 PASS: user constraints, no-implementation boundary, KHTN 8 Outcome proposal status, KHTN 9 conditional boundary, no-migration path, and resolved companion sources are preserved.
- (decision) Update P3.1 before implementation: retain its candidate catalog but supersede automatic five-Lesson bindings and unreviewed prototype UI reuse; the first public pilot uses one source-grounded KHTN8 outcome confirmed by a real reviewer.
- (decision) Parallelize platform pinning and contract v1 work with the Content Tool outcome register and Circuit-cluster review; neither waits for the full KHTN8-9 mapping backlog.
- (constraint) Name an actual qualified curriculum reviewer and an actual scientific/model reviewer before running the real pilot; do not fabricate approvals, and record conflicts of interest and existing distinct-review requirements.
- (constraint) Before starting a second Lab implementation, require one real server-authoritative pilot attempt with persisted result, versioned contract v1, and a passing second-model fixture against the same contract; cap concurrent Lab development at two.
- (constraint) Remove prototype-only Lab definitions, demo entries and unreviewed UI from product flows; retain the existing Circuit engine and generic infrastructure only where verified reusable, and preserve historical attempts and saved experiments.
- (constraint) Preserve open Foundational Lab access without assignment or quiz gating; score and progress evidence remains server-authoritative, while local drafts are never learning evidence.
- (decision) Before fixing version pinning add a reproducible controller regression test. A synthetic fixture shows an active pack ID recorded while the Lab model and separately selected configuration determine the result; this is not live-database evidence.
- (decision) Treat the existing no-migration assertion as unproven for exact pack/model/config pinning and independent releases; reuse existing schema where sufficient and add a migration only if implementation proves it necessary.
- (constraint) KHTN9 topics may inform discovery but receive no released Lab bindings until provenance, mappings and human review meet the accepted standard.
- (decision) Maintain standalone idempotency and F5 draft recovery in the platform track; release each Lab only after reviewed outcomes, scientific model and exact version evidence are present.
- (event) Validation pass 1 PASS: five stable capabilities have intent and success, pilot review gates and open questions are explicit, and version pinning is an identified gap rather than a release claim.
- (event) Validation pass 2 PASS: preserve the candidate catalog and scientific proposal while superseding the five-Lesson automatic binding, unreviewed UI reuse and no-migration assumptions; all seven requested plan adjustments are recorded.

- (evidence) After the scoped BE fix, attempts use the recorded pack model, reject incompatible model/config or numeric pack ranges, and retain an execution snapshot in existing simulationResult JSON; historical attempts remain available and reproduction labels missing snapshots legacy_unverified.
- (constraint) Pack ranges validate compatible independently versioned numeric configuration parameters, but do not establish that each exact pack/config pair was specifically reviewed together. Exact pair approval and launch-time pack selection remain open.
